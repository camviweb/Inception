# Developer documentation

## Set up from scratch

On a fresh Debian or Ubuntu VM:

```sh
sudo apt-get install -y make openssl git
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"     # log out and back in afterwards
echo "127.0.0.1 login.42.fr" | sudo tee -a /etc/hosts
git clone <repo> inception && cd inception
make
```

### Configuration files

`srcs/.env` is created from `srcs/.env.example` on the first `make`. It is git-ignored. Compose reads it for `${...}` substitution in `docker-compose.yml`, and the Makefile includes it to learn `DATA_PATH`.

| Variable | Used by |
|---|---|
| `DOMAIN_NAME` | nginx certificate and `server_name`, WordPress site URL |
| `DATA_PATH` | where the two volumes keep their data on the host |
| `MYSQL_DATABASE`, `MYSQL_USER` | MariaDB setup, `wp-config.php` |
| `WP_TITLE`, `WP_ADMIN_USER`, `WP_ADMIN_EMAIL` | WordPress install. The admin name must not contain "admin" |
| `WP_USER`, `WP_USER_EMAIL` | second WordPress user, role `author` |

### Secrets

`secrets/` is git-ignored. The Makefile creates each missing file with `openssl rand -hex 16`. Hex keeps the values free of quotes, which matters because the MariaDB entrypoint pastes them into SQL. To use your own password, write it into the file before the first `make`.

| File | Mounted into |
|---|---|
| `db_root_password.txt` | mariadb |
| `db_password.txt` | mariadb, wordpress |
| `wp_admin_password.txt` | wordpress |
| `wp_user_password.txt` | wordpress |

Each container reads them from `/run/secrets/<name>` with `$(< file)`. None of them is in an environment variable, a Dockerfile, or an image layer.

## Build and launch

`make` runs `docker compose -f srcs/docker-compose.yml up -d --build`. Startup order:

1. `mariadb` starts. On an empty volume its entrypoint runs `mariadb-install-db`, then `mariadbd --bootstrap` with SQL that sets the root password and creates the database and user. Then it `exec`s `mariadbd`.
2. Compose polls the healthcheck (`mariadb-admin ping` as the `mysql` OS user over the unix socket) until it passes.
3. `wordpress` starts. On an empty volume it copies WordPress from `/usr/src/wordpress`, writes `wp-config.php`, installs the site and creates the second user. Then it `exec`s `php-fpm8.2 -F`.
4. `nginx` starts and serves `/var/www/html` from the shared volume, passing `.php` requests to `wordpress:9000`.

Build or restart one service:

```sh
docker compose -f srcs/docker-compose.yml up -d --build wordpress
docker compose -f srcs/docker-compose.yml restart nginx
```

## Managing containers and volumes

```sh
make ps
make logs
docker exec -it wordpress bash
docker exec -it mariadb mariadb -uroot -p"$(cat secrets/db_root_password.txt)"
docker exec wordpress wp user list --allow-root
docker volume ls
docker volume inspect inception_wordpress
docker network inspect inception_inception
```

Checks worth running before a defense:

```sh
docker exec nginx sh -c 'echo | openssl s_client -connect localhost:443 -tls1_1'   # must fail
docker exec nginx sh -c 'echo | openssl s_client -connect localhost:443 -tls1_3'   # must succeed
docker exec wordpress cat /proc/1/cmdline | tr '\0' ' '                            # php-fpm, not bash
docker exec mariadb sh -c 'kill 1'; sleep 5; make ps                               # comes back up
```

## Where the data lives

| Volume | Container path | Host path |
|---|---|---|
| `inception_mariadb` | `/var/lib/mysql` | `$DATA_PATH/mariadb` |
| `inception_wordpress` | `/var/www/html` (wordpress and nginx) | `$DATA_PATH/wordpress` |

Both are named volumes on the `local` driver with `type: none, o: bind`. The data sits in a host directory you choose, and Docker still lists and manages the volumes. With this driver setup Docker does not copy image content into the volume, which is why the WordPress entrypoint copies the core files itself.

What survives what:

| Command | Containers | Images | Volume definitions | Data in `$DATA_PATH` |
|---|---|---|---|---|
| `make down` | removed | kept | kept | kept |
| `make clean` | removed | removed | removed | kept |
| `make fclean` | removed | removed | removed | deleted |

After `make clean`, the next `make` recreates the volume definitions over the same directories and the site comes back as it was. Only `fclean` starts from zero. It needs `sudo` because the files belong to the container users (`mysql`, `www-data`).

```
Makefile
secrets/                          git-ignored, generated by make
srcs/
  .env.example                    copied to .env on first make
  docker-compose.yml
  requirements/
    mariadb/
      Dockerfile
      conf/90-inception.cnf       bind-address 0.0.0.0, overrides Debian's 50-server.cnf
      tools/entrypoint.sh
    wordpress/
      Dockerfile
      conf/www.conf               php-fpm pool, listens on 9000 as www-data
      tools/entrypoint.sh
    nginx/
      Dockerfile
      conf/nginx.conf             replaces Debian's nginx.conf entirely
```
